# Skein v0.3 — Pilot Intelligence

Skein v0.3 adds an evidence-synthesis layer for design-partner pilots. It does not replace the underlying graph, versioning, compression, MCP, or governance capabilities.

## Experiment model

Run matched engineering workflows twice:

- **Baseline:** repository context assembled using the existing workflow.
- **Skein:** the same task using Skein graph/context and agent communication.

The intelligence layer pairs the runs and combines four evidence streams:

1. Scenario execution evidence — latency, process outcome, output/error proxies, Git change signal.
2. Provider telemetry — input/output/reasoning tokens, estimated cost, success/error outcomes.
3. Reviewed task outcomes — task success, rework, and handoff loss.
4. Skein evidence — retrieval, traceability, version history, and governance signals.

Missing evidence is reported as `NOT MEASURED`; it is never inferred from a proxy.

## Commands

```text
skein pilot-intelligence-init . --pilot partner-a
skein pilot-scenario-init . --name partner-a
# edit .skein/pilot-scenarios.json with matched workflow commands
skein pilot-scenario-run .
skein pilot-intelligence-run .
skein pilot-intelligence-report .
```

## Provider telemetry

Skein's existing JSONL telemetry store accepts real provider measurements through `TelemetryStore.log(...)`. Mark events with metadata `{"experiment":"baseline"}` or `{"experiment":"skein"}` so v0.3 can pair them.

Required fields for economic evidence are `input_tokens`, `output_tokens`, and `estimated_cost_usd`. Reasoning tokens are optional.

## Reviewed task outcomes

Create `.skein/pilot-experiment-metrics.json` only after the pilot owner has reviewed the task outcomes:

```json
{
  "metrics": {
    "task_success_rate": {"baseline": 0.80, "skein": 0.95},
    "rework_per_task": {"baseline": 2.0, "skein": 1.0},
    "handoff_loss_rate": {"baseline": 0.20, "skein": 0.05}
  }
}
```

These values are examples of the contract, not Skein benchmark claims.

## Decision gates

Default v0.3 targets are configurable:

- context reduction >= 30%
- provider/LLM cost reduction >= 20%
- scenario latency reduction >= 10%
- task success >= 90%
- at least one matched scenario

A successful local run is **not** a production-quality claim. A production-quality claim is only permitted by this harness when real provider telemetry, reviewed task success, and matched scenarios are present.

## Outputs

- `.skein/pilot-intelligence-results.json` — machine-readable evidence model.
- `.skein/pilot-intelligence-report.md` — executive scorecard and evidence boundary.

## v0.3 product principle

The purpose of Pilot Intelligence is not to manufacture a favorable ROI number. It is to make Skein falsifiable: a design partner should be able to prove where the system improves context efficiency, economics, coordination, quality, and traceability — and equally where it does not.
